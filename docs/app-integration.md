# Research app integration

`apps/research` is an isolated adaptation; the original source and operator state are preserved separately. `provenance/app-reuse.json` pins every selected baseline file by SHA-256 and records the baseline build and 40 passing tests. No original state, tunnel, built resources, screenshots, private handoff documents or conversation links are copied. Both distributed fixture JSON files now contain synthetic examples under `example.com`; the original real fixture is recorded by hash and origin in the provenance manifest, and remains only in the original checkout.

The app uses its existing MCP lifecycle server and research store. The Python engine retains immutable typed data and dependency closure. The app owns titles, corrections, request scope, parent links, review decisions and archive state. A full local materialization is cached in app state to support exact row lookup and review across the whole dataset. Every engine reference is resolved again on store reads; canonical hash, origin/run identity, schema, capture time and row count are verified. The cache is not a second correction authority.

## Run locally

From `apps/research`, run `npm ci`, `npm run build`, and `npm test` in a clean environment with the root Python package installed in its `.venv`. The initial baseline reused the original checkout's installed dependencies through an ignored symlink. The final dependency update uses a separate `npm ci` installation in this app; the original dependency directory remains unchanged. The OAuth-capable MCP client is pinned to 2.2.0, and a small controlled-output inliner replaces the former glob-dependent build plugin. Each widget embeds its generated JavaScript, CSS and fonts; unexpected external asset references fail the build. `npm start` binds `127.0.0.1:3117`. `npm run stdio` serves a local MCP client. Data directories belong to this copy; set `RESEARCH_DATA_DIR` and `WEBQL_DATA_DIR` explicitly for isolated tests. `WEBQL_PYTHON` can override the root `.venv/bin/python` executable.

HTTP defaults to `fixture-anonymous`: only synthetic fixture data is exposed, the trusted engine principal is `fixture-anonymous`, and private engine access is disabled. Protected HTTP requires `RESEARCH_AUTH_MODE=protected` and `RESEARCH_BEARER_TOKEN`. It resolves one fixed operator-configured `WEBQL_PRINCIPAL`; incoming arguments never select a principal. The local preview host prompts for the bearer token without putting it in a URL. Stdio is a local protected transport. Private computation additionally requires configured engine permission; private data in model-visible tool content requires `RESEARCH_ALLOW_PRIVATE_HOST_DISCLOSURE=1`. Self-hosted storage and cloud-model disclosure are separate permissions. An accepted refresh with private source data marks the parent's effective view private-derived for disclosure checks. Private trees, labels and request questions are omitted from authorized public views and global row lookup. Linked children inherit private context classification.

## Contracts and lifecycle

`webql_capabilities`, `webql_explain`, `webql_query`, `webql_run_status`, `webql_read_result`, `webql_inspect_evidence` and `webql_cancel` use the JSON-lines engine bridge. Responses are bounded and errors are safe. Protected mode forwards configured profile names to the engine, whose trusted configuration enforces live permission, destination grants, credentials and a finite total budget. Anonymous mode only admits fixture profiles and removes configured profile files from its subprocess environment. This build has no live-provider qualification. Queries bind scalar parameters and named original/effective result inputs; larger integer values use lossless strings with explicit SQL casts. Effective inputs resolve one canonical app snapshot, require its exact amendment revision, and materialize effective values through `import_table` with the pinned parent dependency and app revision. The engine retains that revision and reauthorizes dependency closure.

`open_research` and `append_research` accept `result_ref: {result_id, snapshot_id, title}`. The server resolves full local data; the host does not need to copy a whole dataset into its prompt. The normal expansion sequence remains `find_research_row` → `expand_research` → `get_research_request` → `webql_query` → `append_research` → `open_research`. App requests pin the parent and row/field scope before any execution. Completed retries return the existing child; changed payloads conflict; failed/cancelled requests reject late results. Refresh queries use `row_id_column`: the host projects saved IDs explicitly, the engine validates unique IDs against authorized bound inputs and removes that column from the result schema, and the app checks exact tracked scope and columns. URL/name/position remapping is never implicit. Refresh proposals require explicit `review_refresh` decisions. Legacy `verified` means returned textual support under the app review contract, not a truth guarantee.

The baseline requires an exact row for expansion; root/table refresh remains supported. Contextual correction, research links, tree navigation, Back-state restoration, source navigation, rename, archive/restore and host feature detection stay in the original UI. A successful message acknowledgement or save does not establish a host turn or rendered component.

## Snapshots, presentation and export

v1 JSON is preserved verbatim. Its `sourceResultSetId` maps through a tagged `legacy-import` origin helper, and the original date remains declared day precision. v2 has a tagged engine origin, explicit day/instant precision, nullable source URLs, multiple sources, evidence references, full row count and immutable local `dataRef`. New engine runs require an offset-bearing instant and real run ID; imported source identifiers are never fabricated. Inline v2 snapshots enforce actual UTF-8 byte limits. Unknown logical types, unsafe numeric integers, invalid dates/offsets, malformed struct/list values and mismatched schemas are refused.

BIGINT and DECIMAL use lossless strings, DOUBLE uses finite numbers, Boolean stays Boolean, SQL NULL stays JSON null, and declared logical types drive scalar corrections even for all-null columns. Lists and structs display as compact JSON and are read-only. The engine schema and export retain up to 128 columns; the UI displays the first 12. Single-row payloads beyond the app allowance must be projected more narrowly; the full engine data remains retained.

The UI receives at most 100 rows per server window and automatically smaller windows when needed to fit the snapshot byte allowance. `research_page` reads later windows without rerunning the query. Count and window metadata distinguish preview from full data; search/filter controls apply to the current window. `find_research_row`, correction validation and research requests use the entire canonical local dataset, including rows outside the visible window.

`export_research` composes the full selected research tree and engine bundles, preserving originals, amendments, tree, request history and review decisions. `import_research_bundle` restores the state with identity conflicts refused, typed correction validation and dependency authorization. Engine bundles imported into a clean engine store receive local identity mappings; the app reconciles origin/run/hash/capture metadata while preserving app IDs, row values, correction revisions, tree and request linkage. The UI's Import and Export call those tools. Ordinary bounded `import_research` remains available for v1/v2 snapshots. Transport bundle inputs are capped at 16 MB; v1 limits remain unchanged.

All app mutations acquire an atomic filesystem writer lock and reread state and revisions while holding it, across store instances and processes. Competing stale revisions conflict; they cannot overwrite an accepted amendment. A writer waits at most three seconds, then returns explicit busy. The lock has a unique owner token and is released in `finally`; there is no expiry, guessed stale owner or automatic takeover. If a process crashes, first stop and verify all writers for that store, inspect `.writer-lock/owner-<token>.json`, and explicitly remove only that confirmed stale lock directory. Do not remove a lock while any writer may still be active.

The subprocess adapter currently uses a bounded synchronous 30-second response deadline. On POSIX each bridge runs in its own process group; timeout or response overflow stops that owned group, including its SQL worker. Windows uses ordinary child termination; the SQL worker is already unsupported there. Engine query budgets can permit longer work, but pending-handle transport for long runs is not implemented in this app. A timeout is an honest transport failure; inspect/retry the same request key to recover existing run state rather than creating a duplicate paid request.

## Evidence level

The preserved 40 tests cover the existing v1 lifecycle and simulated host messaging. Added tests cover v1/v2 origins and timestamps, large integers/decimals/Unicode/nested/null values, declared all-null correction types, a 205-row full-data lifecycle, revision-pinned effective inputs, full export/reopen, fresh-engine bundle remapping/retry, private/anonymous policies actual bridge principal isolation/private disclosure refusals and an actual JSON-lines bridge admission refusal. A positive 205-row SQL-plus-app lifecycle test is retained; the outer tool sandbox refuses the engine OS sandbox launch, so its execution requires authorized local test execution. Build/test evidence is local. No live provider calls or hosted ChatGPT/Claude qualification is claimed. Composed SQL currently retains input-set lineage; absent final-cell evidence is not converted into fabricated support in the app.
