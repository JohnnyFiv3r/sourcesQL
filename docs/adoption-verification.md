# Adoption verification

A package install, a working gateway and a rendered MCP App establish different
parts of the adoption path. Keep their evidence separate when qualifying a new
release or helping someone connect their own account.

## Published baseline: 0.1.2

The published **0.1.2** wheel was installed into a fresh Python 3.13 environment
outside the checkout on 2026-10-15. Its SHA256 matched the public release. The
installed CLI completed synthetic research, reopened its stored result and
imported its portable bundle without network access. Personal-cloud planning
worked twice with the same digest and recovered through `status`. The default
release download also fetched the exact installed version from PyPI and verified
the published wheel digest. No account resources, Flights or provider requests
were created by these checks. Installed release checks on Python 3.12, 3.13 and
3.14 are also part of the release workflow.

The personal-cloud setup regressions cover account and destination checks,
private credential handling, plan integrity, recovery after uncertain resource
creation, and explicit retries for a failed deployment. These are synthetic API
checks; they do not establish that a newly registered account can complete every
signup, consent or plan requirement.

## 0.2.0 qualification

The wheel and source distribution pass installed qualification outside the
checkout on Python 3.12, 3.13 and 3.14. Controlled app, restricted Docker and
actual Python/SQL-worker checks cover canonical evidence, revised choices,
successor publication, repeatable materialization and subsequent SQL.

Actual ChatGPT and Claude app controls also passed manual evidence inspection,
Accept → Keep → Accept, Skip → Accept for a separate addition, gated publication,
locked decisions after publication, original-table preservation and saved
successor reopening. The fixture engine acquired fresh sources locally; normal
bundle export/import through the documented MotherDuck adapter preserved their
canonical identities, timestamps, hashes and evidence in the existing workspace.
Hosted review/publication then used those stored results. No new Flight, live
provider call or allowance change was needed. This does not qualify the hosted
acquisition stage or broad research quality.

ChatGPT checkpoint saving and fresh-Claude continuation passed with the same
canonical selection/revision. Both hosts also saved, read and cancelled an update
request. Claude's prepared composer message requires Send before its agent
continues. The measured ChatGPT host did not offer checkpoint file download.

Use the authenticated HTTPS MCP connection; there is no packaged-plugin
installation requirement. Refresh host tool definitions and reopen saved data
after an update. Existing hosted Flights embed a pinned wheel and require their
own reviewed runtime upgrade; publishing a package does not upgrade them.

## Clean Hobby onboarding: 0.2.1

The installed 0.2.1 CLI completed the normal plan/apply/resume path
from an empty setup workspace in an existing eligible Hobby workspace, without
prior setup receipts or recovery/repair flags. Setup created a credential-free
static Production placeholder and waited for Ready before installing local
dependencies, provisioning the backend or uploading credentials. Ordinary resume
reused the same attempts, reached Ready with the app in Preview, and assigned the
reviewed alias. All 18 gateway settings were encrypted Preview-only variables.

Exactly one F4 fixture Flight succeeded in 10.733 seconds, returning two rows.
The reviewed hard runtime and daily reservation were each 120 seconds. A fresh
MCP session read the saved result. Native MotherDuck records confirmed one settled
job, one run and one engine result after both host checks, with no provider
reservation or live search/model calls.

ChatGPT and Claude each completed a real OAuth consent/code exchange using a
separate public strict third-party SPA client with authorization-code-only grants,
the host's exact callback and delegated `sourcesql:access` on the new audience.
Neither connection used a client secret or fixed bearer header; the API denied
machine-to-machine access. Both actual inline apps displayed the same saved
two-row table, title and source links.

The earlier Hobby check after reviewed recovery remains separate history: its
single fixture Flight succeeded in 9.35 seconds. The clean check qualifies setup,
bounded execution, persistence and both hosts' OAuth/rendering with existing
accounts. Fresh-account signup, token renewal, live-provider research and the full
client lifecycle remain unqualified. Release artifacts receive their own archive and installed-package checks.

## Verify an adopter's workspace

1. Install the published package outside a source checkout. Run the local fixture
   example and reopen its stored result before configuring paid providers.
2. Prepare an unapplied `fixture` preflight with execution disabled. If one
   bounded fixture job is approved, enable execution before preparing a separate
   plan/workspace intended for apply. Review its account, database, alias, owner
   identity and finite limits, then apply only its exact digest. Keep receipts
   private; `--run-fixture` cannot enable a disabled saved plan.
3. Finish account login, OAuth consent and any exact-domain protection exception
   deliberately. Setup does not create accounts, accept terms, add a card or
   change a subscription.
4. Run the installed `verify` command against the saved plan. Its ordinary path
   checks MCP connectivity and can reopen an existing fixture result without
   submitting a new research job. `--run-fixture` deliberately permits one fixture
   execution and requires that execution was enabled in the reviewed plan.
5. Add the direct authenticated HTTPS endpoint in the intended MCP client. Open
   the saved result and confirm the actual component, source opening, navigation
   and supported actions; a successful MCP response alone does not prove
   rendering or app-message delivery.
6. For continuation, save and reopen a compact checkpoint. Inspect
   its exact revision and selected canonical IDs, then use controlled evidence
   to review a manual update. Change a choice before publication, reopen the
   published successor and confirm the original table is unchanged. Record these
   separately from protocol-only and local-browser checks.
7. Qualify a live provider only under a separate finite allowance. Record the
   exact deployment, provider policy, job ID, result, request count and recovery
   behavior. Keep provider billing distinct from application reservations.

Application reservations are conservative dispatch guards. They are neither a
measurement of provider charges nor an account-wide guarantee that infrastructure
usage remains free. When a daily guard is exhausted, retain the queued job and
resume explicitly after capacity becomes available; do not reset the ledger or
create another namespace to bypass it.
